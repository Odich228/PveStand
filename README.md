# pvestand — TUI для авторазвёртки стендов в Proxmox VE

Программа читает YAML-описание стенда и через REST API Proxmox создаёт пул,
сети, ВМ (клоны шаблонов) и пользователей. Есть текстовое меню (TUI) и
режим без интерфейса (`-run`).

## Сборка

Нужен Go 1.22+.

```bash
go mod tidy          # скачает зависимости и создаст go.sum
go build -o pvestand .
```

Для Linux-сервера с другой машины: `GOOS=linux GOARCH=amd64 go build -o pvestand .`

## Подготовка Proxmox

1. Создай шаблоны ВМ (правый клик по ВМ -> Convert to template) и запомни их VMID.
2. Создай API-токен: Datacenter -> Permissions -> API Tokens.
   Для первых тестов проще взять `root@pam` и снять галку *Privilege Separation*.
   Для продакшена выдай токену права: `VM.Allocate`, `VM.Clone`, `VM.Config.*`,
   `VM.PowerMgmt`, `VM.Snapshot`, `Pool.Allocate`, `Datastore.AllocateSpace`,
   `Datastore.Audit`, `Sys.Modify` (сеть), `Sys.Audit`, `User.Modify`,
   `Permissions.Modify`.
3. Для управления сетью на узле должен стоять `ifupdown2` (в PVE по умолчанию есть).
4. Для отображения IP в «Статус ВМ» в гостевой ОС должен быть установлен и
   запущен `qemu-guest-agent`, а в настройках ВМ включён QEMU Guest Agent.

## Запуск

```bash
cp stand.example.yaml stand.yaml      # поправь под себя
./pvestand
```

При первом запуске без `-c`, `-host` и `-token`/переменных окружения TUI сам
спросит, какой YAML-файл открыть (из текущей папки) и куда подключаться. Если
всё уже передано флагами/переменными — сразу открывается меню.

```bash
export PVE_HOST=192.168.1.10
export PVE_TOKEN='root@pam!stand=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx'
./pvestand -c stand.yaml -insecure    # -insecure для самоподписанного сертификата
```

Флаги:

| Флаг         | По умолчанию         | Что делает |
|--------------|-----------------------|------------|
| `-c`         | `stand.yaml`          | YAML-описание стенда |
| `-host`      | `$PVE_HOST`            | адрес Proxmox |
| `-token`     | `$PVE_TOKEN`            | API-токен |
| `-insecure`  | `false`                | не проверять TLS-сертификат |
| `-parallel`  | `4`                     | сколько ВМ клонировать/удалять одновременно |
| `-log`       | (авто, только в TUI)    | файл журнала событий |
| `-run`       | (нет — открывается TUI) | `plan\|deploy\|destroy\|snapshot\|reset\|status` без интерфейса |

Без TUI (для скриптов):

```bash
./pvestand -c stand.yaml -insecure -run plan
./pvestand -c stand.yaml -insecure -run deploy -parallel 6
./pvestand -c stand.yaml -insecure -run snapshot
./pvestand -c stand.yaml -insecure -run reset
./pvestand -c stand.yaml -insecure -run status
./pvestand -c stand.yaml -insecure -run destroy
```

## Меню TUI

1. **Показать план развёртывания** — список шагов; шаги с «∥» при
   выполнении идут параллельно.
2. **Развернуть стенд** — сначала preflight-проверка (узел, шаблоны, бриджи,
   место на хранилище), затем клонирование ВМ пачками (`-parallel` штук
   одновременно).
3. **Создать снапшот «чистое состояние»** — снапшот `stand-clean` для всех
   ВМ стенда.
4. **Сбросить стенд к снапшоту** — откат всех ВМ к `stand-clean` (для
   пересдачи экзамена/практики без полного передеплоя).
5. **Удалить стенд** — показывает точный список ВМ, которые будут удалены
   (см. «Безопасное удаление» ниже), и удаляет только их.
6. **Статус ВМ** — список ВМ пула: запущена/остановлена, IP-адреса через
   QEMU Guest Agent.

Во время выполнения (`Esc`) можно отменить операцию — уже запущенные шаги
доработают/остановятся, дальнейшие не начнутся.

## Как это устроено

- `internal/pve` — клиент API Proxmox (запросы, ожидание задач по UPID,
  снапшоты, guest agent, проверки узла/хранилища/сети для preflight).
- `internal/stand` — чтение и проверка YAML, построение плана
  развёртывания/удаления/снапшота/сброса, preflight-проверки.
- `main.go` — TUI на Bubble Tea (экран подключения, выбор файла, меню,
  подтверждения, прогресс) и режим `-run`.

Развёртывание — это план (`Plan`) из трёх стадий: последовательные шаги
(пул, сети), параллельные цепочки (по одной на ВМ: клонировать → настроить →
запустить) и снова последовательные шаги (пользователи). Параллельные
цепочки выполняются одновременно, но не больше `-parallel` штук сразу —
это ограничивает нагрузку на хранилище. Повторный `deploy` не создаёт
дубли: существующие пул, сети, ВМ и пользователи пропускаются.

### Безопасное удаление

Каждая ВМ при развёртывании получает тег `pvestand-<имя-стенда>`. При
удалении из пула забираются только ВМ, у которых **имя совпадает с
описанным в конфиге ИЛИ стоит этот тег** — остальное содержимое пула не
трогается. Пул целиком удаляется, только если после удаления «наших» ВМ в
нём ничего постороннего не осталось; иначе пул остаётся, а в логе — заметка
об этом.

### Несколько копий стенда (участники)

В `stand.yaml` можно задать блок `participants` — тогда стенд разворачивается
отдельной копией на каждого участника/команду: свой пул (с суффиксом id),
свои ВМ (тоже с суффиксом в имени) и свои пользователи. «Развернуть»,
«Удалить», «Снапшот» и «Сброс» в этом случае применяются ко всем копиям по
очереди. После развёртывания нескольких копий на экране (и в выводе
`-run deploy`) показывается таблица «участник → пул → логин → пароль».
Пример — см. `stand.example.yaml`.

## Важно

- Пул стенда должен быть выделен под него, но безопасное удаление (см. выше)
  теперь защищает и от случая, если туда попало что-то постороннее.
- Создание и удаление сетей применяет сетевые настройки узла (`ifupdown2 reload`).
  Это кратковременно затрагивает сеть хоста, не запускай посреди занятий на боевом узле.
- Шаблоны клонируются на тот же узел, что указан в `node`.
- Пароли в YAML хранятся открытым текстом. Не коммить файл стенда в git.
- Preflight проверяет место на хранилище приблизительно (по размеру дисков
  шаблона); для связанных клонов — это грубая оценка, а не точный расчёт.
