# PVE Stand Deployer

TUI и CLI для развёртывания учебных стендов в Proxmox VE: клоны шаблонов, изолированные Linux bridges, пулы, пользователи, участники, снапшоты и сброс.

## Быстрый запуск

Нужен Go 1.22+. Клиент изменения ресурсов поддерживается в Linux и macOS; на Windows используйте WSL. Сетевые операции выполняются через REST API, SSH программе не нужен.

```bash
go build -o pvestand .
cp stand.example.yaml stand.yaml
export PVE_HOST='pve.example.test:8006'
export PVE_TOKEN='deployer@pve!stand=YOUR_TOKEN_SECRET'
export LAB_STUDENT_PASSWORD='YOUR_STUDENT_PASSWORD'
./pvestand -c stand.yaml -run validate
./pvestand -c stand.yaml -run doctor
./pvestand -c stand.yaml -run plan
./pvestand -c stand.yaml
```

В YAML замените node, pool и template на свои. Для нового развёртывания выбирайте ещё не занятый пул и новые имена ВМ/пользователей. ВМ и пользователи старой версии не принимаются под управление автоматически; см. [миграцию](docs/migration.md).


## Права Proxmox

Создайте отдельного пользователя и API-токен. При Privilege Separation права требуются и пользователю, и токену. `doctor` читает эффективные разрешения API-токена, включая права с `propagate=0`.

| Объекты | Основные права |
|---|---|
| `/nodes/NODE` | `Sys.Audit`; `Sys.Modify` при создании/применении сети |
| `/vms/TEMPLATE` | `VM.Audit`, `VM.Clone` |
| `/vms` либо `/pool/POOL` для новых ВМ | `VM.Allocate`, нужные `VM.Config.*`, `VM.PowerMgmt` |
| `/vms/VMID` существующих ВМ | `VM.Audit`, нужные `VM.Config.*`, `VM.PowerMgmt`, `VM.Snapshot`, `VM.Snapshot.Rollback` согласно операции |
| `/storage/STORAGE` | `Datastore.Audit`, `Datastore.AllocateSpace` |
| `/pool/POOL` | `Pool.Allocate`; для выдачи ролей `Permissions.Modify` либо допустимое делегирование через `Pool.Allocate` |
| `/access/groups` | `User.Modify` для создания пользователей без групп |
| `/access/realm/pve` | `Realm.AllocateUser` на версиях, где это требуется (проверяется для PVE 9+) |
| `/sdn/zones/localnetwork/BRIDGE[/VLAN]` | `SDN.Use`, включая обычные Linux bridges в PVE 8/9 |

Для удаления сети дополнительно нужен `VM.Audit` на `/vms`, чтобы проверить подключения всех ВМ. При наличии LXC на узле автоматическое удаление сети блокируется до ручной проверки: программа пока управляет только QEMU ВМ. Не выдавайте права администратора только ради прохождения одной проверки.

Некоторые API требуют дополнительных прав в зависимости от версии, устройств и назначаемой роли. Проверка не заменяет авторизацию сервера: точный отказ API и журнал задачи показываются при выполнении. Источники контрактов: [Proxmox AccessControl](https://github.com/proxmox/pve-access-control/blob/master/src/PVE/API2/AccessControl.pm), [QEMU API](https://github.com/proxmox/qemu-server/blob/master/src/PVE/API2/Qemu.pm), [User API](https://github.com/proxmox/pve-access-control/blob/master/src/PVE/API2/User.pm).

## Конфигурация ВМ

Полный пример — [stand.example.yaml](stand.example.yaml).

- `cores`, `sockets`, `memory` в МиБ: 0 или отсутствие означает наследование из шаблона.
- `count`: количество копий, по умолчанию 1. Имена нескольких копий получают номер.
- `cpu`: имя модели CPU; совместимость с физическим процессором окончательно проверяется QEMU.
- `storage`: целевое хранилище при `full_clone: true`; существующие диски автоматически не переносятся.
- `boot_order`: список устройств, например `[scsi0, net0]`.
- `nics`: bridge, model (по умолчанию virtio), vlan (1..4094; отсутствие снимает VLAN с описанного адаптера).
- MAC описанных адаптеров сохраняются. Прочие параметры этих адаптеров сохраняются, кроме VLAN/trunks. `replace_nics: true` удаляет неописанные адаптеры; по умолчанию они наследуются.
- `depends_on`: имена групп ВМ. Все копии зависимой группы ждут успешного завершения всех копий её зависимостей. Циклы запрещены.
- `ready: agent`: ожидание ответа qemu-guest-agent. Агент нужно установить в госте и включить в шаблоне.
- `ready: tcp` и `ready_address: host:port`: ожидание соединения с машины клиента. `ready_timeout` — секунды, по умолчанию 120. TCP-проверка подтверждает доступность порта, а не корректность приложения.
- Без `ready` зависимость считается выполненной после успешного запуска QEMU.

При `participants` каждой копии назначаются отдельные пул, имена и диапазон внутренних bridges. Внешние bridges не перенумеровываются. Копии участников выполняются последовательно; внутри копии действует `-parallel`.

## Журнал состояния, повторный запуск и отмена

В `.pvestand/` сохраняется JSON без паролей и токенов: владелец, VMID, стадии, UPID и созданные ресурсы. Файлы создаются с правами 0600; запись атомарная. Каталог можно задать `-state-dir` или в профиле. По умолчанию он отсчитывается от рабочей папки, поэтому запускайте программу из одной папки или задавайте абсолютный путь.

Сохраняйте резервную копию каталога вместе с конфигом. Потеря состояния блокирует автоматическое принятие существующих ресурсов. Журнал привязан к адресу API, name, node и pool; смена этих полей создаёт другое управление. Нужен исходный конфиг и журнал для удаления старого стенда.

Перед изменением берётся файловая блокировка. Известные незавершённые задачи проверяются по UPID. При повторном запуске программа проверяет фактическую ВМ, её имя и метку в description. Новая ВМ не создаётся только из-за сбоя на этапе её запуска. Работающая ВМ с отличающейся конфигурацией требует явной остановки пользователем.

Esc/Ctrl+C прекращает ожидание и планирование следующих шагов. Уже принятые задачи Proxmox могут продолжить работу. Повторите ту же команду после восстановления связи. Если соединение оборвалось до получения UPID, программа сохраняет прежний VMID и ищет задачу клонирования по исходному шаблону и точному ID назначения в журнале задачи. Найденная задача ожидается без повторного POST. Уже завершённый клон проверяется по владельцу, имени, отсутствию блокировки и наличию дисков шаблона. Поиск ограничен 30 секундами; ожидание найденной задачи — 30 минут. Неизвестный результат блокирует дальнейшие изменения. Незавершённый ошибочный клон не считается исправной ВМ: проверьте его диски или удалите принадлежащие журналу ресурсы и повторите развёртывание.

Повторы с паузой применяются к временным ошибкам настройки. Отказы в правах и завершившиеся ошибки QEMU не повторяются автоматически. При однозначном отказе сервера из-за конфликта VMID выбирается другой номер, максимум 5 попыток. После EOF/таймаута клонирование автоматически не повторяется и другой VMID не выделяется.

Если ВМ и соответствующая задача не появились, можно явно разрешить одну повторную отправку в прежний VMID:

```bash
./pvestand -c stand.region.l2.yaml -run deploy -retry-clone COD-ADMIN -parallel 1
```

Подключение задайте тем же профилем/переменными/флагами, что раньше; запускать из прежней рабочей папки с исходным `.pvestand`. Параметр действует только для незавершённого clone выбранного имени из журнала. Перед отправкой проверяются ВМ и задачи; если исходный запрос всё же был принят, программа возобновляет ожидание или проверяет клон. Чужая ВМ не изменяется. После восстановления продолжается обычный deploy, включая остальные ВМ. Блокировки автоматически не снимаются.

## Защита ресурсов

Для ВМ требуются запись журнала, VMID, имя и точная метка description. Совпадения имени/общего тега недостаточно. Для созданных пулов, bridges и пользователей сохраняются записи и метки в comment/comments. Не удаляйте эти служебные метки вручную.

Уже существующий bridge используется без присвоения владельца и остаётся после destroy. Сеть с чужими подключениями, физическими портами или IP узла не удаляется. Пул удаляется только при отсутствии любых участников, включая LXC и хранилища. Пользователи вне журнала не изменяются и не удаляются. Снапшоты и сброс применяются только к подтверждённым ВМ стенда.

Сетевая конфигурация узла применяется через ifupdown2. Не запускайте изменение сети без учёта нагрузки и текущей конфигурации хоста. Программа не может обеспечить транзакцию вместе с ручными действиями администратора или другим инструментом.

## Профили и секреты

```bash
cp profiles.example.yaml profiles.yaml
export PVE_LAB_TOKEN='deployer@pve!stand=YOUR_TOKEN_SECRET'
./pvestand -profile lab -c stand.yaml -run doctor
./pvestand -profile lab -c stand.yaml -run deploy -credentials credentials.txt
```

В профиле хранятся host, insecure, state_dir и ссылка token_env либо token_file. Пути профиля отсчитываются от файла профилей. Явные флаги имеют приоритет; `PVE_HOST` имеет приоритет над адресом профиля. `PVE_TOKEN` используется как запасной источник, если профиль и флаги не задали токен.

Пароль пользователя задаётся ровно одним из `password`, `password_env`, `password_file`. Путь password_file отсчитывается от YAML стенда. Файлы секретов должны иметь права 0600/0400. Произвольные переменные по всему YAML не подставляются.

Токен и известные пароли маскируются в ошибках/журналах; автоматического вывода таблицы паролей нет. Явный `-credentials` сохраняет таблицу в файл 0600. Не коммитьте реальные конфиги, журналы состояния, токены и выгрузки паролей.

## Интерфейс

План и подтверждения прокручиваются PgUp/PgDn. Во время выполнения показаны имя ВМ, VMID, этап, результат и длительность. `l` переключает таблицу/полный журнал; PgUp/PgDn прокручивают журнал, `f` оставляет ошибки. В завершённом deploy выберите ВМ стрелками и нажмите `r`, чтобы повторить её и зависимости. Esc отменяет ожидание; Enter возвращает в меню.

## Разработка и проверка

```bash
make check
make release VERSION=local
```

CI проверяет форматирование, vet, тесты с race detector на Linux/macOS и Go 1.22/stable. Сборки для Linux/macOS amd64/arm64 сохраняются в артефакты CI. Тесты используют HTTP transport в памяти и не обращаются к Proxmox.

`cli.go` — CLI/флаги/сигналы, `ui_model.go` — модель и команды TUI, `ui_update.go` — обработчики, `ui_view.go` — отображение. `internal/stand/service.go` объединяет выполнение TUI/CLI; `state.go` хранит состояние; `deploy.go` строит и выполняет планы; `preflight.go` проверяет окружение; `internal/pve` реализует REST API.

Ограничения: реальный кластер, guest-agent и сетевые изменения требуют отдельной интеграционной проверки. RAM оценивается без накладных расходов QEMU, связанные диски — приблизительно как 10% исходных. Проверка не гарантирует CPU/ISO/passthrough-совместимость и будущую доступность ресурсов. Автоматического отката всего стенда, присвоения старых ресурсов и удаления сетей при LXC пока нет.
