# Один конфиг — десять стендов

PveStand 2026.10.27.5 разворачивает одну топологию для списка участников. Все ВМ одного участника находятся на одном узле. Несколько узлов должны принадлежать одному кластеру: используется один API endpoint и журнал. Отдельные независимые кластеры требуют отдельных запусков и профилей.

## Конфиги

- `stand.region.10.example.yaml`: все A0–A9 на SF-4.
- `stand.region.10.multinode.example.yaml`: пример 5+5. `REPLACE-NODE2` и VMID 2001–2012 являются примерами, их нужно заменить на существующий узел и его локальные шаблоны. Сам файл не создаёт узлы, storage или шаблоны.

В обоих примерах 15 ВМ на участника, 64 ГиБ RAM и 31 настроенный vCPU на стенд: всего 150 ВМ и 640 ГиБ RAM без накладных расходов. На SF-4 с 251,5 ГиБ общей памяти все десять в этих размерах не поместятся. Профиль RAM не уменьшен автоматически. Нужны дополнительные узлы либо отдельно проверенный облегчённый профиль образов. Оценка дисков linked clones остаётся приблизительной; рост записей гостей и снапшотов нужно контролировать.

## Размещение

```yaml
node: SF-4
nodes:
  OTHER-NODE:
    templates:
      1001: 2001
      # Полная карта всех используемых исходных VMID -> локальный VMID.
participants:
  - id: A0
    bridge_base: 1001
    users:
      - id: Competitor-A0@pve
        password_env: REGION_COMPETITOR_PASSWORD
  - id: A1
    node: OTHER-NODE
    bridge_base: 1101
    users:
      - id: Competitor-A1@pve
        password_env: REGION_COMPETITOR_PASSWORD
```

Это фрагмент: networks и vms описываются один раз в полном примере. `nodes.<node>.storage` задаёт целевое хранилище для полных клонов (`full_clone: true`). Linked clones сохраняют хранилище локального шаблона. Межузловое клонирование с параметром target в этот режим не входит: подготовьте локальные шаблоны на каждом выбранном узле. VMID уникальны в кластере, поэтому их нельзя повторно назначить разным локальным шаблонам.

Для A0 получатся пул `region-A0`, имена `GW-1-A0` и т.д., мосты vmbr1001–vmbr1015. Для A1 — region-A1 и vmbr1101–vmbr1115; для A9 — region-A9 и vmbr1901–vmbr1915. Эти номера не являются VLAN. Внутренние мосты не имеют физических портов. При перестановке участников с явно заданным bridge_base адреса их мостов сохраняются. В старых конфигах без bridge_base по-прежнему используется позиционный сдвиг; не переставляйте такие участники после создания ресурсов.

У каждого участника должен быть отдельный пользователь. Все примеры используют одну ссылку REGION_COMPETITOR_PASSWORD; при необходимости задайте каждому свой password_env/password_file. Существующая учётная запись от другого стенда автоматически не принимается и не перепривязывается. Если Competitor-A0@pve уже принадлежит прежнему журналу, используйте другое имя либо отдельно подготовьте переход.

## Проверка и запуск

```bash
cp stand.region.10.example.yaml stand.region.10.yaml
./pvestand -c stand.region.10.yaml -run validate
./pvestand -c stand.region.10.yaml -run plan -offline
```

Эти команды не подключаются к Proxmox и не читают секреты. Для реальных действий настройте PVE_HOST/PVE_TOKEN или профиль, а также REGION_COMPETITOR_PASSWORD локально.

```bash
./pvestand -c stand.region.10.yaml -run doctor
./pvestand -c stand.region.10.yaml -run deploy -parallel 1
./pvestand -c stand.region.10.yaml -run status -participant A0
./pvestand -c stand.region.10.yaml -run snapshot -participant A0
./pvestand -c stand.region.10.yaml -run reset -participant A0
./pvestand -c stand.region.10.yaml -run destroy -participant A0
```

`-participant A0` также работает с doctor, plan и deploy. Без флага (или с `-participant all`) выбраны все. При выборе одного участника его секреты читаются отдельно от остальных. В TUI нажмите `p` в главном меню и выберите все стенды либо один A0–A9; выбранный охват виден в заголовке и действует для всех пунктов меню.

Перед deploy проверяются все выбранные узлы и пулы. Нехватка RAM даже на одном узле блокирует новые изменения. Если несколько узлов используют storage с shared=1, суммарный расход сравнивается с общим свободным объёмом. Участники создаются последовательно; -parallel ограничивает число обрабатываемых ВМ внутри одного участника. Весь стенд должен успешно завершиться перед переходом к следующему. Это не транзакция: принятые операции Proxmox могут продолжиться при потере связи.

Для восстановления EOF у конкретного клона используйте полное имя:

```bash
./pvestand -c stand.region.10.yaml -run deploy -participant A0 -retry-clone COD-ADMIN-A0
```

## Журнал

Сохраняйте прежнюю рабочую папку или абсолютный -state-dir и API endpoint. Имя batch, базовый node и pool определяют файл журнала. Участники внутри него имеют свои scope и VMID. После создания ресурсов journal закрепляет node и набор внутренних мостов. Правка node/bridge_base не считается миграцией и блокируется; для удаления используйте исходный конфиг. Сначала завершите удаление выбранного стенда, затем меняйте его размещение. Уже существующий одиночный region1 автоматически не становится участником A0.

## LLDP/LACP

```bash
./pvestand -c stand.region.10.yaml -run l2manifest -out region-l2.manifest.json
```

JSON содержит только топологию, узлы, участников и хеш scope; паролей, токенов и journal owner в нём нет. Перенесите JSON и `scripts/prepare-region-l2.py` на каждый целевой узел. После полного развёртывания его стендов выполните от root:

```bash
python3 prepare-region-l2.py --manifest region-l2.manifest.json --check
python3 prepare-region-l2.py --manifest region-l2.manifest.json --apply
```

Узел определяется по hostname. Если его короткое имя отличается от имени в Proxmox, исправьте соответствие прежде чем применять настройки. `--participant A0` ограничивает проверку и применение одним стендом. По умолчанию должны существовать все стенды текущего узла из карты. Код 2 при --check означает, что нужны настройки масок; 1 — несовпадение схемы/ошибка. Все выбранные стенды проверяются до первой записи; при ошибке записи предпринимается откат уже изменённых масок.

LLDP разрешается на внутренних TAP, LACP — на параллельных кабелях между одной парой ВМ (в региональной схеме PROVIDER-SW/PROVIDER-GW). Перед записью проверяются владельцы, состав NIC, отсутствие tag/trunks, firewall/link_down, vlan_filtering/STP и ровно два ожидаемых TAP на мосту. После stop/start ВМ TAP пересоздаются: скрипт нужно повторить.

Внешний vmbr0 остаётся общей WAN-сетью. Раздельные пулы и внутренние мосты не изолируют WAN-интерфейсы: адреса и доступ через общий uplink нужно организовать отдельно. VLAN/IP/LACP внутри гостевых систем программа не настраивает.
